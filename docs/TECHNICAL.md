# AstroSophy 技术与使用说明

## 应用能力

- Flutter/Dart Android 手机应用；相册选择、拍摄、星场检测、天区解算、测量展示均在设备内运行，不要求用户配置或维护自建服务器。
- 图片分析先缩放到最大边长 1200 px，再计算稳健背景、背景噪声、饱和比例和紧凑亮点；星点检测放在独立 isolate，避免阻塞 UI。
- 选好图之后可以先圈出取景范围，只有那一块会被分析和（必要时）上传；解析可以放到后台跑，跑完自动存进观星仓库。
- 月面照片在分析的最一开始就被分流出来，走独立的月面链路：给出月盘位置与半径、亮面占比（图内数像素），配合拍摄时刻再给出相名与盈亏；结果页在月亮上画一个圈并标出亮面占比。认出月面时会**先问一句**：直接报告月亮，还是继续寻找其他天体。不选就不往下走——继续的那条路在解算失败时会把照片上传，而上传是整条链路上唯一不可逆的动作。月球照里星点链路整个不跑——在月面上找“星”找到的只是环形山和噪点。见 [`docs/TECHNICAL.md` 的“测量边界”第 10 条](#测量边界)。
- 点源形态使用局部亮度加权二阶矩估计长短轴比；明显拉长的候选不参与恒星坐标匹配和 Gaia 标定测光，并提示其可能为拖线、失焦或处理伪影。单张图不能据此确认卫星或飞机。
- 首次启动显示整屏四页新手引导（导入星图 / 本机解析 / 看懂结果 / 保存回看）；各卡片的“？”可随时查看该指标的解释，顶部问号可随时重播引导。
- 解算成功后把视场内的星座连线投影到像素坐标、裁剪到图像范围内，叠在标注图的最底层，并标注星座名；同一份数据也驱动“这片天在哪儿”那张全天图（等距圆柱投影的全天示意图，标出中心坐标和视场大小）。连线和全天图都是纯几何，本机解算与在线解算共用一套代码。
- 结果页的图内亮点列表按“亮星 / 亮点 / 可疑飞线”分成三组，每组可折叠，也能整组把圆圈从图上隐去或显示回来（默认只显示亮星那一组）。分组只是显示方式：每项记的是它在全局编号里的下标，所以列表里第 7 项和图上标着 ⑦ 的永远是同一颗星。判“有没有名字”用的是图上标注星名的那套判据和同一个阈值，两边不会各说各话。
- **系内天体**（行星、矮行星、小行星、彗星）和深空天体一样在“图上目标”里单列一组，位置紧随深空天体之后，**初始就在图上画着标记**（那是用户按下快门时想拍的东西），也能逐项、整组或一次性隐去。内置 16 颗亮小行星（灶神星 6.5 等、谷神星 7.8 等，全部 ≤ 12.5 等）、10 颗矮行星和全部 939 颗彗星；落在画面里但亮度不够、图上没能对上时照样写一句「它今天在这儿，亮度 X 等，拍不到」，而不是静默省略。判据与边界见 [`docs/TECHNICAL.md` 的“测量边界”第 16 条](#测量边界)。
- 看图区可以双指缩放和平移，圆圈、编号和星座连线和图在同一棵被变换的子树里，所以放大时跟着一起放大，指的还是那颗星；放大后右上角会出现一个“回到整幅”的按钮，因为把比例精确捏回 1 倍并不顺手。
- AI 解读按 Markdown 渲染（`lib/markdown.dart`），标题、粗体、列表、引用、代码块、表格和链接都会排版后显示，不会把 `##`、`**` 原样留在屏幕上；`==高亮==` 渲染成主色，用来标天体名。链接只显示文字，不跳转。不认识的语法当普通文字显示，宁可少排版也不吞内容。
- 结果页最上面那段「拍到什么」是**本地拼的 Markdown**（`buildHeadlineMarkdown`），不走模型：星座、星名、编号、星等、视场全是星表和解算给出的既成事实，编错一个字符就是错的事实。模型拿到的是同一份事实，它写的那段解读接在这后面——模型的活是解释，不是生产这些名字。
- 月面照片走独立链路，在分析入口**最一开始**分流；报告顶部换成相名与两个亮面占比，画面上标出月盘圆圈。
- 启动器图标与引导页插画（吉祥物 Nox 及另外三页）由 Recraft 在开发期生成（前者渲染为 Android 多密度及自适应图标资源，后者栅格化为 PNG 后随应用分发）；Recraft 凭据不进入应用或仓库，见 [`tools/make_onboarding_art.py`](../tools/make_onboarding_art.py)。
- 图片选择支持常见图片和相机 RAW 文件。RAW 解码尝试在容器中查找最大的嵌入式 JPEG 预览；不同相机格式和厂商编码差异很大，因此不是完整 LibRaw 支持，也不是对传感器原始线性数据的分析。

## 本机天区解算

内置目录（`assets/catalog/`）由 [`tools/build_catalog.py`](../tools/build_catalog.py) 离线生成，幂等可重跑：Hipparcos 主表的 41,394 颗星（截至 V=8.0）连同 Bright Star Catalogue 的名称、[`lib/solver.dart`](../lib/solver.dart) 里的解算器全部在手机上运行。另有一层 Gaia DR3 的背景星（G < 11，120.6 万颗，`gaia.bin` 约 8 MB）给窄视场兜底；这层在解算时被**当作两层用**：先只用其中 G < 9 的那 14 万颗，解不出来才动用整层。深度由 `--gaia-mag-limit` 控制，界线由 `--gaia-mid-mag-limit` 控制。

解算分四步，全部离线：

1. **建索引**：为目录里每颗星找角距最近的若干邻居，两两三点组成三角形，用「次长边/最短边」和「最长边/最短边」两个比值当指纹——它们对平移、旋转、缩放、翻转都不敏感。
2. **取图内三角形**：从检出的星点里挑最亮的若干颗当种子，每颗同样取最近的若干邻居组三角形。
3. **粗匹配**：指纹对上即得到三点对应，据此解出「像素坐标 → 切平面坐标」的相似变换。同一个指纹上的候选按「比值接近」排序，三个顶点的**亮度次序**也和图内端对得上（两边差值都超过 0.4 等的才算数）的排在最前面——星表一密，形状碰巧一样的假候选会有几千个，没有这一条，真正的那个会被挤到队尾。
4. **验证精修**：把目录星投影回图像数内点，内点够多就接受，再用全部内点最小二乘，并迭代把切点挪到像面中心。解认定之后还会把内点补全一次——组三角形用的那 8 颗只负责「找到」解，报告里的匹配星数和星等零点则按最大那一档（120 颗）的规模重新投影、重新数一遍，这一步只是投影加查表。

关键取舍是两边都按「最近邻居」而不是「最亮邻居」组三角形：最近邻居给出的三角形边长自动等于当地的星间距，所以图内和目录两侧的三角形尺度天然接近；换成最亮邻居，广角照片里最亮的星彼此隔十几度、窄视场里最亮的星都在视场外，两种极端都会让尺度对不上。

也正因为两侧必须用**同一套近邻关系**，星表要分层用，而且图内端参与组三角形的星数要按档试着来：图内端只拿最亮的若干颗检出，一颗亮星的近邻必然是亮星；目录端若把 Gaia 那上百万颗暗星并进主星表，同一颗亮星的近邻会变成旁边的暗星，两侧枚举的就不再是同一批三角形——实测猎户座的合成星图会因此从「解得出来」变成「解不出来」。所以浅层（只有 Hipparcos）先试，失败了才建、才用更深的层，深层的索引只在需要时才构建。

图内端那「若干颗」从 8 颗起，依次试 8 / 16 / 24 / 120，第一个成立就收。这条阶梯两边都拉不开：取太少，图里的暗星会把目录星的近邻顶掉；取太多，结果一样。视场越窄，落进画面的目录星越少，而深叠加的照片里检出动辄几千颗——Seestar S50 的对角线视场只有 1.45°，那片天区里亮过 G < 9 的目录星只有几颗，图内端取 24 颗就等于塞进去十几颗目录里根本没有的星。

目录三角形的比值用球面角距算，图内三角形用像素距离算。两者在 TAN 投影下相差 O(θ²)，对几度视场只有万分之几，远小于指纹容差，省掉投影让建索引快得多。

**内点门槛不是一个常数**，而是按每张图自己算出来的。一个候选变换由三组对应关系定义，那三颗必然算内点；剩下的图内星点每落进某颗目录星附近 3 像素以内就再算一个。假解能凑到几个「额外的」内点，取决于「撞上一颗目录星」有多容易：

```
p ≈ 图内星点数 × π × 3² / 像面面积        期望假解数 ≈ C(目录星数, 额外内点) × p^额外内点 × 验证预算
```

取最小的「额外内点数」，使期望假解数低于 1e-3，再压到上限 10 颗。于是：400×320 的小图、视场里 80 颗目录星时算出 10 颗（和过去手调出来的常数一致，宽视场行为一个字节都没变）；675×1200 的智能望远镜照片、视场里只有十几颗目录星时降到 6 颗。门槛之所以敢降，是因为概率本身降了——同样的 675×1200 像面上，凑出额外三个内点的概率比小图低两个数量级。

**适用视场**：视场里大约要有 6～20 颗目录星才能解算，具体几个由上面的概率算出来。视场下限是 1°（原先写死 3°，把智能望远镜的每一张照片都挡在了门外——Seestar S50 对角线 1.45°、S30 2.44°，放开之后实测四张照片里三张当场解出）。再窄、或者这片天区目录星实在不够，就交给在线服务。

**分三层试，前一层不成就加深一层。** 顺序是：主星表（Hipparcos，V ≤ 8，4.1 万颗）→ 主星表 + Gaia 里 G < 9 的那批（共约 17 万颗）→ 整张表（Gaia 到 G < 11，共约 125 万颗）。每一层的索引只在真要用到它时才建，建一次就缓存住，同一台机器上下一张图不用再建。

分层的理由在上面已经说过一半：两侧必须用同一套近邻关系，所以目录端不能一股脑塞进百万颗星。另一半是**代价**——三角形索引的大小和星数是同一个量级，最深那层要建一分钟上下、常驻几十 MB，而绝大多数照片在第一层就出结果（三张演示图 6～7 秒），窄视场的目标在第二层也够了。不该为解得出解的图付最深那层的账。

实测（桌面 JIT，一张 1.9° 视场的合成星图，视场里只有二十几颗目录星、其中亮过 G<9 的只有个位数）：

| 阶段 | 耗时 |
| --- | --- |
| 主星表索引（4.1 万颗） | 5 秒 |
| 主星表按 8/16/24/120 四档试完并放弃 | 9 秒 |
| 中间层索引（17 万颗） | 8 秒 |
| 中间层按四档试完并放弃 | 4 秒 |
| 最深那层索引（125 万颗） | 62 秒 |
| 最深那层匹配 | 1 秒 |
| 合计 | 90 秒 |

一片天区的索引只建一次：同一台机器上解第二张图时，前面那几行都在缓存里，只剩匹配那几秒。界面因此在最深层换一套配色并在进度条左端写「本地深度思考」，见 [`lib/widgets.dart`](../lib/widgets.dart) 的 `SkyProgressBar`。

## 在线服务

- **Astrometry.net**：本机解算失败、且用户勾选授权后，把分析预览 JPEG 上传至 `nova.astrometry.net` 解算，轮询任务状态并取回 WCS。
- **Gaia DR3（ESA 归档 TAP）**：拿到 WCS 后查询视场内的恒星位置与 G 星等，用于标定星等零点和散布；用视场中心坐标，不上传照片。
- **SIMBAD（CDS TAP）**：按解算视场查询星名与深空天体，并在本地做坐标交叉匹配；没有手工枚举恒星清单。
- 低质量或无法解算的图片仍提供本地降级分析；不会在无坐标时猜测天体名称。

## 测量边界

1. **相对仪器星等**：本地检测星点的像素通量相对值，只能比较当前同一图像中的亮度，不是校准视星等。
2. **Gaia G 星等**：把 Gaia 星与 4 px 内的检出点源配对（要求置信度 ≥ 0.25、G 在 4–18 等之间），取星等差的中位数作零点，散布为 1.4826 × 中位绝对偏差；参考星少于 5 颗时不报告零点。设备光谱响应、白平衡、JPEG 曲线、饱和、镜头暗角等会带来系统误差，散布值不包含完整误差预算。
3. **孔径测光**：由全帧统计出的 PSF FWHM 决定孔径与天空环带半径，扣完天空背景后累加通量；星等误差只含光子噪声与天空背景估计误差，不含前述系统误差。
4. **天空背景视觉指数**：像素背景亮度归一化后的指标，受到曝光、ISO、白平衡和后期处理强烈影响，不是现场光污染测量，不能解释为 SQM 或 Bortle 等级。
5. **非星空掩膜**：用亮连通域面积、Sobel 梯度与行列方向的直线密度识别文字、表格、界面截图和大亮斑，掩膜内的像素不参与星点检测；结果给出非星空占比，占比过高时质量判为“较弱”并提示这可能不是纯星空照片。这是启发式判断，不是完备的内容分类器。
6. **质量提示**：由紧凑点源数、背景 MAD、饱和比例和局部点源形态生成；线状候选不是卫星/飞机分类器，也不是完整的云量或前景遮挡模型。
7. **用户判断**：只有拉长的候选需要用户自己下结论。结果页给每一条配一对 ✓ / ✗，判为 ✗ 的从星表匹配、测光、报告和模型摘要中排除，但仍留在图上和列表里（颜色变淡，编号保留），随时可以改回来。标记存在 `DetectedStar.isRejected` 上，保存时一并写进档案，重开这条记录还能改。这是结果页上唯一会改动数据的开关，所以它只长在可疑飞线上——亮星和亮点是算出来的结论，不该由一次误点改写。
8. **圆圈的隐去**：每组标题旁的 − / + 只控制图上画不画那一组的圆圈，卡片标题旁的那一对一次管全部（亮星、未匹配星点、可疑飞线、深空天体、系内天体）。隐去就是完全不画——不画圈也不画编号，而不是画淡一点或打个叉，因为那仍然是画面上要费神忽略的东西。这是纯显示开关：测量结果、报告、星表匹配和存下来的档案都不受它影响，也不写进历史。
9. **星座连线**：连线是对每个星座的亮成员跑最小生成树自动生成的示意轮廓，不是 IAU 的官方星座图，也不用于任何测量。全天图用等距圆柱投影，极区变形明显，只能回答“大概在哪儿”，不能用于定位。
10. **图上的文字标注**：文字之间会互相避让（`LabelPlacer`）——先给优先级高的排，后来的挪到附近空位并拉一条细线指回它标的那个点；实在放不下就不画那一段。不画是有意的：两段压在一起的文字哪一段都读不出来，而每个标注在下面的列表里都有一行，图上没有不等于丢了这个对象。只有「这张图上唯一的结论」（月面圈、疑似行星）例外，它们排不下也会就地画出来。排布全程无随机数，同一张图每次画出来的位置一致。
11. **导出的标注图**：按**原始分析尺寸**重画一遍，不受屏幕缩放影响；画的是当前勾选的那一套标注。导出走系统分享面板，文件同时落在应用文档目录的 `exports/` 下。导出会把带标注的图交给用户选择的第三方应用，这一点由用户自己决定。
12. **取景裁剪**：裁剪改的是**字节**，不是显示。裁完之后分析、预览、以及可能的上传都只看这一块，历史记录里存的也是这一块。裁剪会丢掉嵌入的 EXIF，所以已经读到的拍摄时刻要显式带过去——否则裁一刀就把「这张照片几点拍的」丢了，而月相和行星位置全靠它。
13. **进度条的三种配色**：薄荷绿＝本机在算；琥珀＝照片已经交给在线解算；红＝**本机解算已经成功**，照片一次都没离开设备。红色在别处通常表示出错，这里刻意反过来用，因为它只在照片确实没出去的时候出现。判据是 `PipelineProgress.solvedLocally` 这个字段，**不去认阶段文案**——文案是给人读的，改一句话就会悄悄改掉一条判断。
14. **深空天体的名字只有一处规则**（`deepSkyCaption`）：有中文常用名就用它，没有才退回「编号 · 类型」。同一个名字出现在图上标注、图内亮点列表、深空天体卡和报告正文四处，各写一遍迟早漏一处——曾经就漏过：报告里写「M 16 鹰状星云」，图上标的却是「M 16 · 星团与星云」。
15. **观测记录的名字**（`月亮_261015`）在本机拼，不调模型：名字的两个部分（拍到了什么、哪天拍的）都是已经算出来的结论，不需要判断。让模型来做等于把一次确定的映射换成一次会编的取样，还要联网、要花钱、要等。模型可以**改**它——用户说「改名叫第一次拍的月亮」，那是用户的意思，不是猜测。没有拍摄时刻就只留前半截，不拿「今天」冒充。
10. **月面与月相**：月面照片走独立分支，在分析入口**最一开始**做定性分流——大而圆的亮斑（亮面 ≥ 画面 0.5%，外缘有一大段贴在同一个圆的圆周上）直接判为月面，不再进星点流程。之所以要前置，是因为现有星点判据会把月面当成正常星场，在一张真实月球照上“检出”13 颗星，报告里的星等和噪声就全是编的。月面分支给出两个互相独立的数：
    - **图上量出来的亮面占比**：阈值取「天空均值 + 2σ」（σ 由月盘外的天空实测），数出被照亮的像素数再除以月盘面积。月面是球，投影到画面是正圆，明暗界线投影成半个椭圆，亮面占整个圆的面积比恰好等于亮面占比，所以直接数像素就是准的。阈值必须定在“刚好看得出比天空亮”而不是“亮度减半”：明暗界线是光照趋近于零的地方，拿峰值一半当门槛会把整条界线过渡带判成暗面（实测一张真实月球照因此量出 60.8%，而星历说 82.6%）。
    - **按拍摄时刻算出来的亮面占比与相名**：Meeus《Astronomical Algorithms》第 47 章 47.2/47.3/47.4 三个基本角加第 48 章 48.4 的相位角式、48.1 的 `k = (1 + cos i)/2`，`waxing = 平角距 D < 180`。忽略 ΔT（70 s 只让 k 动 1×10⁻⁴，比 48.4 自身的 0.005 小一个半数量级），不加章动（做角距时日月章动自相抵消）。
    **相名和盈亏只能靠时刻**：单张照片里相机有没有镜像、有没有上下翻转是看不出来的（加天顶镜的折射镜是镜像的，牛顿式是旋转的），光看图说不出在盈还是在亏。两个数都摆进界面，差得超过 5 个百分点就提示拍摄时刻可能不对。
    月面测量在四张非月球演示图上全部返回“不是月面”，没有误报。
16. **系内天体（行星 / 矮行星 / 小行星 / 彗星）**：判据是**两条同时成立**——星表里这个位置查不到星，而且星历算出的位置上有一颗检出到的亮点。只看前一条会把噪声和坏点都算成行星；只看后一条会在满场恒星的密集天区里胡说八道。两件事的顺序也是刻意的：先找候选、再拿候选自己的位置去问星表；反过来（先按预测位置问星表）在星历偏出几角分时问的就是另一个地方的事。
    - **位置来源分两套，容差也分两套**：太阳、行星来自代码里写死的 JPL Standish Table 1 近似根数表（1800–2050 有效，容差 8′，实测土星照片曾需要 4.3′）；小行星和彗星来自构建时抓取的内置表（`assets/catalog/smallbodies.json`，小行星容差 4′、彗星 8′）。按天体给容差而不是全局一个数：容差每放宽一倍，随机吻合的机会就多三倍。
    - **先按亮度筛，再比位置**。全部 939 颗彗星一起比，8′ 容差下随机吻合的期望接近 4.6 个；按拍摄时刻的亮度先筛到 14 等以内（约 80–110 颗），期望降到 0.4 左右。这不是性能优化，是误报控制。同时滤掉大距 20° 以内的天体——它们只在暮光或白天的天空里。
    - **小行星和彗星一次只报偏移最小的一颗**，行星不受此限（同一张照片上同时拍到木星和土星是可能的，而且两边判据各自独立）。
    - **精度实测**（两体传播对 JPL Horizons）：模型本身好于 1′，漂移全靠表变旧——谷神星当天 0.10′、+1 年 0.69′、+3 年 19.8′、+10 年 34.7′；彗星近抛物线那一支（Barker 方程）0.33–1.24′。所以报告里必须印出表的构建日期。
    - **彗星不给亮度数字**：全部 939 颗里 753 颗（80%）的 k1 是 MPC 在没有实测光变曲线时填的缺省值 4.0，算出来的亮度可能差好几等。这个值照样参与「够不够亮」的筛选，但不写进报告。手机分辨率也分辨不出彗尾，所以「认出彗星」只能是「亮点 ＋ 星表无星 ＋ 星历位置吻合 ＋ 亮度够」。
    - **偏心率 ≥ 1.05 的那一颗（1I/'Oumuamua，e=1.1993）没有收进来**：它需要真双曲的通用变量法（Stumpff 级数），而视星等 23 等，永远拍不到。收进来的 939 颗里 825 颗走椭圆开普勒、114 颗走 Barker 方程。
    - **拍不到的照样说**：内置目录里那 10 颗矮行星（冥王星 14.6 等，鸟神星 17.1、妊神星 17.2、阅神星 18.6、共工星 21 等）在小口径器材上一颗都拍不到，但落在画面里时报告照旧写「它今天在这儿，亮度 X 等，这个器材拍不到」，不静默省略。这些条目在图上**一个记号都不画**——画了就等于宣称看见了。而且一次最多说 3 颗，按亮度取最亮的。
17. **图上四类目标用四种记号**，互不相同：亮星与检出点源是薄荷绿实线细圆（拉长的画椭圆）；深空天体是粉色实线圆，圆的大小跟着天体自身的角尺寸走；行星与矮行星是琥珀色**虚线圆 ＋ 十字**；小行星与彗星是浅蓝色**四角取景框 ＋ 十字**。换形状而不是只换颜色，是因为这两类的位置来路不同（行星用代码里的近似根数表，小行星彗星用构建时抓的内置表），而只靠深浅区分色觉障碍用户读不出来。虚线一律表示「按表算，它在这儿」，不是「我看见了」；十字是星历算出的位置，它和圆/框之间错开的那点距离就是这个结论的不确定度。

## 隐私与联网

- API Key 使用 Android Keystore 支持的安全存储保存在当前设备；不会写入仓库文件。
- 照片默认不出设备：本机分析与本机天区解算都不联网。
- 可选 Astrometry.net 解算只有在用户勾选确认后才开始，并将分析预览 JPEG 上传至 `nova.astrometry.net`。请求设置 `publicly_visible=n`，但不能保证第三方数据留存或绝对保密。
- Gaia TAP 查询只发送解算得到的中心坐标和视场，不上传原始照片。
- 星名与深空天体目录查询发送视场坐标至 SIMBAD TAP 服务。
- 导出标注图时文件先写在应用文档目录，再交给系统分享面板；之后去哪个应用由用户在当时决定，应用本身不上传它。
- 普通 Agent 对话只收到本地质量指标、天体名和测量摘要，不接收照片或 Key；只有用户调用历史查询工具时，对应观测的文字摘要才会发送给模型。模型 Key 会发送到用户输入的 Base URL；只应填写可信服务地址。
- Agent 的固定工具只覆盖当前报告、当前视场目录对象（含系内天体）、太阳系小天体的即时位置、本机观测摘要，以及保存/改名/删除、在线解算和视觉遮罩建议。写入或联网动作由 App 展示具体内容并要求逐次确认；工具调用最多 5 次/轮。没有任意文件、URL、Shell 或代码执行工具。内置小天体表是随包分发的静态数据，查它不联网、不发送照片。
- 只有用户明确确认“把照片发给模型”后，才会将当前缩放预览发送到设置里的模型 Base URL。模型输出的归一化矩形会经过坐标、数量和面积校验；应用遮罩前还要再次确认。遮罩只改本机分析输入，不裁剪、不改写原图。
- 启用 Agent 需由用户自行在“本机 API 设置”填写 Key。DeepSeek、OpenAI、OpenRouter 和硅基流动模板仅预填 OpenAI 兼容 Base URL 与模型名，不内置 Key。视觉遮罩不单配“视觉模型名称”，用的就是当前可用模型，因此那个模型需要支持图像输入。模型名、视觉输入和工具调用支持可能变更，请以服务商控制台为准。自定义服务须兼容 `/chat/completions` 请求格式。
- 未启用解算或 Agent 时，图像读取、星点检测和画质诊断不需要网络。
- 演示星图（`assets/demo/`）由作者本人拍摄，提交前已裁掉画面底部的相机信息条——那一条里含拍摄地坐标。

## 保存与历史

- 存档写在应用私有目录下，一条记录由 `<id>.json`（测量结果与解算结果）和 `<id>.jpg`、`<id>_processed.jpg` 两张图组成，没有索引文件：目录本身就是唯一的事实来源。
- JSON 最后写入。写到一半掉电只会留下一个不会被列出的半截文件，不会出现“列表里有、点开是空的”这种情况。
- 存的是缩放到 1200 px 的预览图，不是原图——原图在用户自己的相册里。代价是从历史记录里重新解析时能测到的最暗星等会略浅，星点位置不受影响。
- 删除一条记录会连图片一起删掉；界面会显示历史记录占用的总空间。
- 重命名只改 JSON 里的 `name` 字段：id 不变，两张图片也不搬。为了一个名字去改文件名，会在最坏的时刻留下半搬完的状态，而收益只是文件名的可读性。名字留空视为没改。
- 每条记录按结果分三档描边：绿色＝解算成功（有 `SolveResult`），黄色＝只检测到星点但没解出天区，红色＝没检测到星点、或那张图被判定为非星空。判定同时用描边颜色和角上一个文字角标表示，只用颜色的话色觉障碍用户读不出来。三档里的“非星空”这一项靠摘要里的 `starfield` 字段，它是后加的，老记录读不到时按星点数是否为零兜底。

## 代码结构

- `lib/main.dart`：入口、主题、主界面编排（选图 / 一键解析 / 结果页 / 保存退出）。
- `lib/analysis.dart`：图像解码、星点检测、孔径测光、非星空掩膜与分类、处理图生成。
- `lib/catalog.dart`：内置亮星目录与星座数据的加载和查询。
- `lib/solver.dart`：本机离线天区解算（三角形指纹匹配 → 相似变换 → 内点精修）。
- `lib/astrometry.dart`：Astrometry.net 上传与轮询，以及 Gaia DR3 / SIMBAD 查询。
- `lib/model.dart`：OpenAI 兼容模型服务的双模型路由。
- `lib/pipeline.dart`：一键解析流程与后台 isolate（`SkyWorker`）。
- `lib/report.dart`：爱好者报告（表格、直方图分箱、摘要与建议）。
- `lib/moon.dart`：月相算式（亮面占比、盈亏、相名），只要拍摄时刻。
- `lib/moon_disc.dart`：从照片里量月面（阈值、连通域、最小外接圆、圆整度门禁）。
- `lib/deepsky_names.dart`：深空天体的中文常用名短表（手写，只收常见目标），以及界面上写这个名字的唯一一处规则。
- `lib/smallbodies.dart`：内置太阳系小天体目录（亮小行星、矮行星、彗星）的两体传播与两套亮度律（H/G 相位律、M1/k1 律），以及「先按亮度筛、再比位置」的工作集选择。抛物线那一支用 `orbit.dart` 的 Barker 方程。
- `tools/build_smallbodies.py`：离线生成 `assets/catalog/smallbodies.json`（JPL 小行星数据库接口取根数与 H/G，MPC 的 `CometEls.txt` 取彗星根数与 M1/k1）。
- `lib/naming.dart`：观测记录的名字（`月亮_261015`），本机拼、不调模型。
- `lib/jobs.dart`：后台解析的任务与编排，「保存并退出」靠它。
- `lib/crop.dart`：取景裁剪框与按字节裁剪。
- `lib/nox.dart`：助手 Nox 的对话界面与它对这个应用的自我介绍。
- `lib/export.dart`：按原始图像尺寸把带标注的图重画成 PNG，再交给系统分享面板。
- `lib/history.dart` / `lib/history_screen.dart`：存档读写与历史记录页。
- `lib/markdown.dart`：自写的 Markdown 渲染器，用于 AI 解读。不引 `flutter_markdown`（已停止维护），要处理的语法只有模型实际会用的那几种，几百行的转换器比一个长期没人管的依赖更好交代——也和这个项目“图表全部自绘、不引图表库”的选择一致。
- `lib/onboarding.dart` / `lib/widgets.dart` / `lib/theme.dart`：引导页、共享组件与配色。
- `tools/build_catalog.py`：离线生成星表与星座数据；`tools/make_onboarding_art.py`：生成引导页四页插画。
- `android/`：Android Manifest、应用入口和 Gradle 配置。
- `test/`：合成星场、测光、解算、报告、存档与界面测试。

## Android 启动与测试

1. 安装 Flutter stable SDK、Android Studio 和 Android SDK。
2. 运行 `flutter doctor`，接受 Android SDK licenses，并准备 Android 模拟器或开启 USB 调试的实体设备。
3. 在仓库根目录运行 `flutter pub get` 和 `flutter run`，或双击 `START.bat`。
4. 运行 `flutter test` 和 `flutter analyze` 执行项目验证；仓库的 GitHub Actions 会在每次推送时跑这两步、构建 debug APK，并把 APK 作为产物上传，保留 30 天。
5. 仓库中的 release APK 使用本机 Android debug keystore 签名，仅供个人设备安装；若有合法许可并另作分发，须按 Flutter Android 文档配置正式签名凭据。不要把 keystore 或密钥提交到 Git。

小天体那份表由 [`tools/build_smallbodies.py`](../tools/build_smallbodies.py) 在**构建时**抓一次，之后不再变动，所以表里带着构建日期（`smallbodies.json` 的 `built`，也出现在界面和 Nox 的回答里）。这件事必须让用户看得见：实测谷神星的位置在表建好后一年偏 0.69′、三年偏 19.8′、十年偏 34.7′——**漂移全靠表变旧，而不是算法不准**。

星座连线不是抄自任何星图的现成画法，而是对每个星座最亮的成员跑最小生成树（按角距加权）自动生成的，因此不引入第三方星图数据的授权问题。

应用启动图标与引导页四页插画（含吉祥物 Nox）由 [Recraft](https://www.recraft.ai/) 在开发期生成，凭据不进入应用或仓库。运行时用到的第三方服务是 [Astrometry.net](https://astrometry.net/)、[ESA Gaia 归档](https://gea.esac.esa.int/archive/) 与 [SIMBAD](https://simbad.cds.unistra.fr/)，均为可选功能，说明见上文“隐私与联网”。
