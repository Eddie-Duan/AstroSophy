# 星表扩展建议：行星 / 彗星 / 小行星与 M·C·IC 深空天体

> 结论先行：写这份文档时星表**只有恒星**，本地链路只认点源，所以「动星」和「星云」
> 都识别不出来。本文给出根因定位与四档改进方案。**四档现已全部落地**（A → C → B → D），
> 下面各节保留了当初的计划，并逐条注明实际做成了什么、哪里和计划不一样、以及
> 哪些是明确没做的。

## 一、现状核实

| 项目 | 事实 | 依据 |
| --- | --- | --- |
| 星表内容 | 41,394 颗**恒星**（V ≤ 8.0）+ Gaia 补充层 136,872 颗（G < 9.0），共 178,266 颗 | `assets/catalog/catalog_meta.json` |
| 数据来源 | Hipparcos `I/239/hip_main` + 亮星星表 `V/50/catalog` + 星座边界 `VI/42/data` + Gaia DR3 `I/355/gaiadr3` | 同上 `sources` 字段 |
| 星座连线星等 | 4.6 | `catalog_meta.json` 的 `line_mag_limit` |
| 生成方式 | VizieR `asu-tsv` 取表，脚本自带 `--mag-limit` / `--line-mag-limit` 参数 | `tools/build_catalog.py` |
| 本地解算 | 三角形匹配，需 ≥ 4 个检出点源、足够内点 | `lib/solver.dart` |
| 检星方式 | 阈值图 + 连通域 + 集中度筛选，产出 FWHM / 轴比 | `lib/analysis.dart` |
| 拉长判定 | `axisRatio >= 2.2` 视为拉长（拖线），**被排除在解算之外** | `lib/models.dart`、`lib/solver.dart` |
| 在线链路 | astrometry.net 解算 → Gaia DR3 定位 → SIMBAD 取名与分类 | `lib/astrometry.dart` |
| 深空天体 | 在线时靠 SIMBAD 的 `isDeepSky` 标出，但只画位置不参与本地解算 | `lib/astrometry.dart` |
| 拍摄时间 | 已能读出来：自写的 EXIF 解析只取时间三件套（DateTimeOriginal / 拍摄设备写入的文件时间 / GPS 时间戳）＋时区偏移，读不到时由用户手填 | `lib/exif.dart`、`lib/main.dart` |

### 四个具体缺口

1. **星表无深空天体**：M31 这类目标在 `stars.json` 里不存在，本地永远标不出名字。
2. **星表太浅（≤ 8.0 等）**：窄视场拍星云/行星时，画面里 ≤ 8 等的恒星屈指可数，
   `solver.dart` 的三角形匹配凑不出足够候选 → 本地解算失败，只能回退在线。
3. **只认点源**：星云是弥漫结构，集中度低，多数进不了 `DetectedStar` 候选；
   即便进了，解算也只用非拉长的点源。
4. **没有时间维度**：行星/彗星/小行星的位置随日期变化，必须结合拍摄时刻查星历才可识别。
   时间这一环已经补上（`lib/exif.dart` 读 EXIF，读不到就请用户手填），缺的是星历本身。

### 已经做对的部分（要保留）

- 在线链路里 SIMBAD 的 `otype` 分类已覆盖星系、星团、星云、HII 区、SNR；
- 深空天体是**按目录坐标直接换算像素**，不依赖点源检出，所以标位置本身是可靠的；
- 链路的降级设计（`pipeline.dart` 的 `warnings`）允许某一环失败而整体不中断。

## 二、改进方案

### A. 快速见效（不改数据，约 1–2 天）——**已完成**

| 编号 | 改动 | 涉及文件 | 验收 |
| --- | --- | --- | --- |
| A1 | 让弥散/略拉长的亮源也能进入解算候选：单独放宽用于解算的轴比与集中度门槛，而不是全局改 `isElongated` | `lib/analysis.dart`、`lib/solver.dart` | 用 `assets/demo/demo_m31.jpg` 本地解算成功率上升 |
| A2 | 解算失败时给可操作提示（开在线解算 / 补拍摄时间 / 换宽场），而不是只说「星点不足」 | `lib/pipeline.dart`、`lib/main.dart` | 失败路径的 `warnings` 文案可执行 |
| A3 | 把在线已识别到的深空天体渲染成「M31 · 旋涡星系」并写入报告，而非只画一个点 | `lib/astrometry.dart`、`lib/report.dart`、`lib/widgets.dart` | 报告出现「画面中的深空天体」条目 |

> A1 要注意：放宽门槛会引入更多假点源，必须同时保留「解算候选」与「展示用检出」两套过滤条件，
> 否则界面会被伪星点刷屏。

### B. 星表扩容（解决窄场解算率）——已实现，实测见下

- 用 **Gaia DR3** 补一层 `G < 9.0` 的星，落在 `assets/catalog/gaia.bin`，
  定长 7 字节一条（赤经 3 + 赤纬 3 + 星等 1）。
  - 打包入口是 `tools/build_catalog.py --gaia-mag-limit 9.0`，数据源 `I/355/gaiadr3`；
    与 Hipparcos 重合（5″ 以内）的不重复收录，`catalog_meta.json` 记了
    `gaia_mag_limit` / `gaia_count` 和来源。
  - 实测：13.7 万颗、936 KB；加进原有目录后总资源 2,872 KB，仍在 3–4 MB 预算内。

#### 实测结论：必须分两层用，不能并成一张表

三角形指纹要求「图内端」和「目录端」用**同一套近邻关系**。图内端只用最亮的
120 颗检出组三角形，一颗亮星的近邻必然是另一批亮星；目录端一旦掺进大量
8–9 等的暗星，同一颗亮星的近邻就换成了旁边的暗星，两侧枚举出来的根本不是
同一批三角形。实测（合成星图，`solver_test` 同一套夹具）：

| 天区 | 只有 Hipparcos | 合并成一张表 | 分两层 |
| --- | --- | --- | --- |
| 猎户座 10″/px | 445 ms | 2,379 ms | 47 ms |
| 猎户座 20″/px | 19.7 s | **解不出** | 0.5 s |
| 南天 187°,−61° | 137 ms | **解不出** | 0.5 s |

所以 `PlateSolver` 现在按层走：浅层只用 Hipparcos（V ≤ 8），失败之后才建、
才用深层（含 Gaia 补充层，近邻取 4、三角形少一个量级，索引约 34 MB、建一次
3.7 s）。星多的天区在浅层就出结果，深层只服务浅层星数本来就不够的天区。

另外加了「亮度次序」排序：候选三角形的三个顶点亮度次序和图内端对不上、
且两边差值都超过 0.4 等的，判定为巧合，排到验证队列后面。没有这一条时，
真正的那个候选会被几千个形状巧合的假候选挤到队尾，M45 一张图要跑 10.3 s；
加上之后 0.57 s。这一步把两层的耗时都拉回了原来的量级。

遗留：`demo_m31`（星系本体被检成上千个假星点）和 `demo_vesta`（画面里星点
远比 G < 9 的目录星多）两张实拍图仍然解不出来。前者是检出质量问题
（风险 1），后者需要更深的一层（G < 11 上下），都不在 B 的范围内。
`demo_m45` 端到端正常：本机解算出坐标 → 标出 M 45（110′）→ 报告写明
「是这张照片的主体」。

### C. 离线深空天体目录（离线也能标 M / C / IC，约 3–5 天）——**已完成**

1. 打包精简 DSO 目录：Messier 110 + NGC/IC 主要成员，
   字段取「主名、RA、Dec、类型、角尺寸、视星等」，约几千条、几十 KB。
2. 新增加载器（可与 `catalog.dart` 共用分格索引思路），在**本地解算成功后**、
   未走在线链路时也能做坐标 → 像素换算并标注。
3. 报告新增「画面中的深空天体」段落：名称、类型、角尺寸，并与用户像场尺寸对比，
   说明「这个目标占画面多大比例」。
4. 反向提示：命中 DSO 时，明确告诉用户「这是一张深空目标照片，星点稀疏属正常」，
   避免用户误判为失败。

### D. 太阳系运动天体（行星 / 彗星 / 小行星）——**已完成**（行星 + 太阳）

前置工作做的和原计划**相反**，这是刻意的：

- 原计划是把 `pickImage` 改成 `requestFullMetadata: true`，然后从完整元信息里取
  `DateTimeOriginal`。实际没有这么做：完整元信息里还有 GPS 位置和设备标识，而这
  一节只需要一个时刻。现在的做法是 `lib/exif.dart` **只解时间标签**（`requestFullMetadata`
  保持 `false`），不碰位置、不碰设备型号，也不往归档的位置字段里写任何东西。
  读取失败时界面上给一张卡片让用户手填日期和时刻——把「读不到」变成一个可完成的
  动作，而不是一个错误。手填的是当地挂钟时间，时区未知，和「EXIF 里只有时间、
  没有偏移」的情形走同一条路（按本机时区算，并写进报告说明这是一条假设）。
- 演示图的信息条在入库时就裁掉了（含私人位置信息，见 `lib/demo.dart`），所以
  三张演示图都读不到 EXIF 时间——手动填写那条路是唯一能走通的那条。

数据来源：走**离线**，但没用原计划里那张「截断 VSOP87」的路线图。用的是 JPL
太阳系动力学组 Standish 那份 *"Approximate Positions of the Major Planets"*
**Table 1** 的近似根数（历元 J2000.0，每儒略世纪的变率，有效区间 1800–2050）。
理由：VSOP87 的项数是为角秒级精度付的钱，而这里的判据容差是角分量级（见下），
多出来的精度换不到一个更硬的结论，却要多几百行系数。表本身由用户从页面上原样
贴出后逐字抄入 `lib/ephemeris.dart`——**不凭记忆写**，因为同一条搜索摘要里木星的
半长轴出现过两个不同的值。这份表怎么验的、验住了什么，见
`test/ephemeris_test.dart` 的开头。

识别流程（三条都按原计划实现了）：

1. 用已有的 WCS + 拍摄时刻算目标视位置（`lib/orbit.dart` 解开普勒方程；
   `lib/ephemeris.dart` 是那张根数表；黄道转赤道用 **J2000 的黄赤交角**，
   因为恒星表本来就是 J2000 坐标，用当日交角会带上岁差偏差）；
2. 与检出点源对照，命中容差内则标为「疑似运动天体」；
3. 判定规则两条同时满足才下结论：**星表里查不到对应恒星 + 位置与星历吻合**。
   写进 `lib/moving.dart`，报告正文、给模型的摘要、以及图上的标注三处都带着
   不确定度（角秒差）而不是只给一个名字。

容差取 2 角分（`ephemerisToleranceArcmin`）。这个数不是「星历有多准」，是
「星历有多不准」：近似根数在内行星上可以差到角分量级，再叠加解算本身的像素
尺度误差。放宽它的代价是不对称的——放宽只会让「亮点对上了」更容易成立，而
另一半判据（这一带星表里没星）拦住了绝大多数误报。

**没做的**：彗星和小行星。原计划里写了「亮小行星/彗星用 MPC 轨道要素」，但那张
表只有八大行星和地月质心；`demo_vesta` 这张演示图里拍的是 4 Vesta，而现在对它
没有任何星历，所以那张图上不会出运动天体的结论。太阳不用单占一行，从地月质心
的根数取反方向就能算出来（`sunPosition`）。

## 四、风险清单

1. **假点源**：放宽检星门槛会引入噪声，必须分离「解算候选」与「展示检出」两套判据。
   `demo_m31` 的星系本体确实被检成 3,400 多个「星点」，但**它们不是 M31 解不出来的
   原因**——逐条量过：最亮的 120 颗里一颗都不落在掩膜区域内（最大区域只有 187 像素，
   背景扣除把星系那层平滑的辉光减掉了，剩下的杂点散在整个盘面上）；它们脚下的背景
   也不高（中位数 1.05 倍天空，只有 4 颗超过 3 倍）；它们也不成团（最近邻间距中位数
   42.5 像素，随机取样的对照组是 39.3 像素）。

   真正的原因是**两侧星数不对称**：图内端拿最亮的 120 颗去组三角形，而 M31 这半
   天区在 4.18° 视场里只有 58 颗目录星（Vesta 一带 33 颗，M45 天区 128 颗）。多出来
   的那几十颗把真正的近邻顶掉，两侧枚举的就不是同一批三角形了。这也解释了为什么
   M45 一直能解——那个天区的目录星比 120 还多，图内端根本没有多余的杂点。

   修法是把「图内端用几颗」也变成要试的档位，从小到大试、第一个成立就收，见
   `PlateSolver._imageStarRungs`（现在是 24 和 120 两档）。修完三张演示图都本机解出。

   代价量过了，这是本机解算最贵的一条路。`test/demo_solve_test.dart` 里的
   `demo_m31` 会打两个数：**首次 7,312 ms、预热后 4,173 ms**（2026-10-15，
   开发机）。两个数之差约 3.1 s，和风险 2 里单独测的「建索引 3.7 s」是同一件
   事——深层索引是懒建的，`PlateSolver.warmUp()` 只暖浅层那一半，所以**用户
   拍到的第一张稀疏天区照片要多等这 3 秒**。

   两个口径要说清楚：一，这是 Dart VM 在开发机上的数，不是手机的数——手机上
   是 AOT 编译的 ARM 代码，数值循环通常更快，但 CPU 慢得多，两边不抵消也不
   等价，真要报给用户就得在真机上量。二，档位减到两档之前实测是 9.2 s，现在是
   4.2 s：失败的那一档很贵，它要把验证预算跑满才肯认输，而多一档换不来新的天区
   （实测 24 和 48 要么一起成功、要么一起失败，M31 在 24/48/80 都成、96 以上
   都不成）。
2. **资源体积**：已实测，2,872 KB（Gaia 补充层 936 KB），在预算内。
   代价主要不在体积而在**索引内存**：整张表建索引约 34 MB / 3.7 s，所以深层索引
   必须按需构建、不能开机就建，也不能和浅层合并（见 B 节实测表）。
3. **错误断言**：行星识别一旦时间或坐标错位就会给出错误结论，
   必须同时要求「星表无对应恒星」与「星历吻合」，并在报告中保留不确定度说明。
4. **隐私**：这一节最后是**没往线上走**的那条路。星历是本地算的（内置根数表 +
   开普勒方程），所以「行星在哪」这个问题不需要联网，也不需要用户授权；
   EXIF 只解时间标签，不读位置和设备型号；照片、坐标、时间都不出设备。
   D 没有给在线链路增加任何新的上传面。原先那条「在线星历查询涉及上传」的
   顾虑随着离线方案落地而不成立了。
5. **既有测试**：`test/` 下已有 `solver_test.dart`、`photometry_test.dart` 等，
   每次改动后应跑最小相关用例，避免破坏现有行为。

## 五、开工清单的执行情况

原清单四条：跑测试基线 → 按 A1/A2/A3 顺序改并逐张演示图实测 → 再评估 C 的数据来源
与字段裁剪 → B / D 单独立项先验数据再动代码。四条都按这个顺序走了，A、C、B、D
四个阶段全部落地。清单本身不再需要，留在这里的部分是它结出来的东西：

| 阶段 | 留下的东西 |
| --- | --- |
| A | 检星门槛与「展示检出」分离；失败提示；**分档星数**（见风险 1） |
| C | 离线深空目录（Messier 110 + NGC/IC），报告里的「占了画面多大」 |
| B | Gaia 补充层 13.7 万颗，两层分开走；按需建索引（见风险 2） |
| D | 离线星历（行星 + 太阳）、两条判据、图上标注、报告与摘要（见 D 节） |

**明确没做的，和为什么**：

1. **彗星、小行星**：原计划里写了（「亮小行星/彗星用 MPC 轨道要素」），但内置
   那张表只有八大行星和地月质心。`demo_vesta` 拍的正是 4 Vesta，而它对这张图
   出不了结论。补它要另找一份根数来源。
2. **真图上的行星端到端**：三张演示图里都没有行星，所以「星历位置落在真实照片
   的第几个像素」这件事没被真图验证过。合成用例证明得了判据和报告的一致性，
   证明不了这一件。
3. **手机上的耗时**：风险 1 里的 7.3 s / 4.2 s 是开发机 Dart VM 的数，不是
   手机的数。要写进用户可见的话术就得在真机上量。

**从现在起的规矩**：上面四节里的每一条新结论都配了会失败的测试，改动之后跑
`flutter test`。没有一条结论是靠「看着对」留下来的。
